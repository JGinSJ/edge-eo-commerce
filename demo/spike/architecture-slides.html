01The problem

The answer is buried under the page.

A support or product page is mostly chrome — nav, mega-menus, promos, footers. An AI model executes no JavaScript and reads top-down, so it burns thousands of tokens before it reaches the point, if it reaches it at all. Wrong or missing citations follow.

Feeding bots a prioritized, answer-first payload lifted citation accuracy from 25–30% to over 60% in the customer's own proof-of-concept.

02The pattern — content negotiation at the edge

One URL. The edge inspects who’s asking and hands each visitor the right representation.

No second URL, no origin change, no impact on human traffic — the same cached render, served four ways.

👤 A person

Full live page

The untouched origin page. The EdgeWorker never fires — nothing changes for humans.

🔍 Search crawler

Full HTML + structured data

Googlebot, Bingbot render JS and read schema.org — they get the whole page.

🤖 AI crawler

Skinny HTML

ClaudeBot, GPTBot, Google-Extended — chrome stripped, a fraction of the tokens.

✨ Answer engine

Prioritized · grounding layer

Perplexity, OAI-SearchBot — chrome stripped and the answer hoisted first.

Routing is a policy, not code per page — the same crawler-policy the demo runs, mirrored at the edge.

04Producing the variants — two models

Where the prioritized payload comes from.

High-value pages earn a hand-built grounding layer; the long tail is handled automatically. Both land in the same cache and route the same way.

Model A · high-value

✨ Grounding-layer ingest

The customer's own pipeline generates the prioritized HTML (their agent's tear-down-and-rebuild). It's published to us, we cache and serve it per-bot. We own delivery, routing, and freshness — not their content model.

Model B · the long tail

🤖 Edge-derived, no manual work

Skinny — a per-template transform strips chrome deterministically. Auto-prioritized — an LLM reads any page, finds the answer, and rewrites it answer-first with no config and no marker.

05Origin sync — the #1 concern

Edge-cached, but never stale.

A reshaped, cached page must not drift from origin — wrong price, wrong device, wrong instruction. Three mechanisms keep the variant honest without giving up cacheability.

  • 1Publish-driven purge. The customer's CI/CD fires a refresh on republish — the variant regenerates in lockstep. No drift window.
  • 2Content-hash revalidation. Each variant stores the origin hash; past a short TTL the edge revalidates and re-derives if it moved.
  • 3Live holes for volatile fields. The stable semantic body stays cached; price and availability are pulled live at serve time via an edge-side include.

Served response

live hole — $349 · in stock  edge-side include, never cached

This is the answer to “your price might be wrong” — the objection that makes this an edge problem, not a static side-URL.
